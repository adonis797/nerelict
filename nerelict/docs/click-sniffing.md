# 页面点击捕获：识别「点开才加载的浮层播放器」

面向一个问题：**视频在点击之前不存在**。很多站点的列表页只有一个封面 / 一张卡片，
用户点下去之后才创建播放器、才去请求 m3u8，而且播放窗口是浮层弹窗（lightbox、模态层、
iframe 播放器）直接盖在页面上。

被动嗅探（包 fetch / 扫 performance / 扫 `<video>`）在这类页面上只有三种结果：

- 一个都扫不到（点击前没有任何媒体请求）；
- 只能扫到页面里其它无关视频（广告、推荐位、预加载的下一集）；
- 扫到一堆分片，但不知道它们属于哪一次点击、哪一个视频。

点击捕获就是补这一段的：把「用户的这一次点击」和「之后 8 秒内出现的媒体」关联起来，
并判断这次播放是不是浮层形态。

---

## 1. 适用场景

**适用**

| 场景 | 典型形态 |
|---|---|
| 列表页 / 剧集页点封面播放 | 卡片 + 封面图，点击后弹层出现播放器 |
| 短剧、短视频信息流 | 点击条目后全屏浮层起播，滑动切换 |
| 付费墙 / 试看 | 点击「试看」后才请求带签名的播放列表 |
| 播放器懒加载 | `<video>` 一开始 `preload=none`、无 `src`，点击后才赋值 |
| iframe 播放器 | 点击后插入 `<iframe src="player.example/embed/...">` |

**不适用（明确不做）**

- DRM（Widevine / PlayReady）：能拿到地址也解不开，不在支持范围；
- 纯 Canvas / WebGL 自绘播放器、WebRTC、原生 App 内嵌播放：页面里没有可下载的媒体地址；
- 需要验证码 / 人机校验才能触发的播放：由用户自己完成校验，捕获只记录结果；
- 直播录制：捕获到地址可以播放，但录制不在本功能范围内。

---

## 2. 识别与判定逻辑

### 2.1 三层判定，缺一不可

**第一层：这条 URL 是不是媒体**

按路径后缀判定，与现有嗅探器保持同一套规则：

| 后缀 | 归类 | 去向 |
|---|---|---|
| `.m3u8` / `.mpd` | `playlist` | 资源列表，可播放 / 可下载 / 可解析清晰度 |
| `.ts` / `.m4s` | `segment` | 挂到同目录所属视频，不单独成项 |
| `.mp4` `.m4v` `.mov` `.webm` `.mkv` `.flv` | `progressive` | 只做浮标入口，不进 HLS 资源列表 |

`blob:` / `data:` 一律不进媒体判定——它们不是可交给系统播放器的地址，
改为发一条 `mse` 事件走兜底（见第 5 节）。

**第二层：这次请求是不是「这次点击」引起的**

点击时开一个归因窗口（`ATTR_MS = 8000`），窗口内出现以下任一信号即算命中：

1. `fetch` / `XMLHttpRequest.open` 出现媒体地址（外部播放器库最常见）；
2. 点击后新增 `performance` 资源条目（兜住 Worker 内发起、或包装之前发出的请求）；
3. 新插入的 `<video>` 有 `src` / `currentSrc` / `<source>`；
4. `HTMLMediaElement.play()` 被调用且元素有地址（元素早就存在、点击后才起播的情况）。

窗口内同一地址只记一次；跨会话允许重复（同一集被点两次 = 两次捕获）。

**第三层：这次播放是不是「浮层」**

对播放器元素及其 6 层祖先做打分（0~100），达到 **50** 才标记浮层：

| 信号 | 分值 |
|---|---|
| 元素本身是 `<video>` 或 `<iframe>` | +30 |
| 元素内部包含 `<video>`（弹层容器） | +40 |
| `position: fixed` | +25 |
| `position: absolute` 且 `z-index >= 10` | +15 |
| 覆盖面积 ≥ 55% 视口 | +20 |
| 覆盖面积 ≥ 30% 视口 | +10 |
| 存在半透明深色遮罩（该层为 `fixed`/`absolute`，α ≥ 0.45，覆盖 ≥ 50% 视口） | +10 |
| `class` / `id` / `role` 命中 `modal|popup|overlay|dialog|mask|lightbox|layer|player|float|fullscreen|sheet` | +15 |
| 点击后新插入（点击前快照里没有） | +15 |

典型得分：

- 普通内联播放器（静态定位、页面中段、点击后新插入）：**45**，不标浮层；
  深色主题页面上也是 45——遮罩分只给「定位过的深色铺满层」，
  整页背景色不会被当成遮罩（这条是实测踩出来的）；
- 点击后插入的浮层播放器：30 + 15（新）+ 25（fixed）+ 20（面积）+ 15（类名）= **100**；
- 复用隐藏容器、点击后改成 `display:block`：靠遮罩与类名通常落在 **65~85**。

阈值放 50 是刻意的：它把「新插入但内联的播放器」挡在外面（45 分），
只放行几何或类名明确像弹窗的容器。

### 2.2 多视频共存时不会串味

同一个页面可能有 20 个视频。判定链路不依赖「页面只有一个视频」的假设：

- 每条命中都带自己的 `url`，聚合仍按「规范化地址 + 目录分组」收敛；
- 归因只决定「这条命中属于哪次点击」，不合并不同地址；
- 浮层分数挂在资源项上，取历次命中的最大值，不会被后来的低分覆盖。

## 3. 对点击交互的捕获需求

这是整个功能最容易出错的地方：**必须能拿到点击，又不能影响点击。**

| 需求 | 做法 | 原因 |
|---|---|---|
| 早于站点自己的处理器 | `document.addEventListener('pointerdown', ..., {capture:true})` | 不少站点在 `mousedown` / `touchstart` 就切源，等到 `click` 已经晚了 |
| 不阻断站点行为 | 全程 `passive: true`，脚本里不出现 `preventDefault()` / `stopPropagation()` | 一旦阻断，站点自己的播放器就不弹了 |
| 键盘 / 脚本触发也能覆盖 | `click` 兜底：`pointerdown` 后 1200ms 内不重复开会话 | 避免一次点击算两次，同时覆盖键盘激活 |
| 记录点击对象 | 标签名、首个 class、`innerText`（向上找 3 层）、坐标 | 面板里要能显示「第 3 集」，否则用户分不清哪次捕获 |
| 记录点击时刻的基线 | 当前 `performance` 条目数、当时已存在的 `<video>` 集合 | 前者做差异归因，后者判断「新插入」 |
| 点击后的观察 | `MutationObserver`（`childList` + `subtree`）+ 0/300/800/1500/2600/4200ms 六次扫描 | 弹层通常有动画，插入那一刻尺寸还不完整，需要复评 |
| 生命周期 | `pagehide` / `beforeunload` 清定时器；换页由 Dart 侧重置 | 避免在已卸载的上下文里空转 |

点击本身**不需要**用户额外操作：脚本常驻，任意一次点击都会开窗口；
没有媒体出现就什么也不上报，正常浏览不会产生任何资源项。

## 4. 多视频并发处理方式

### 4.1 会话模型

一次点击 = 一个会话（`sessions`），环形缓冲最多 6 个，超出丢弃最旧的并清掉它的定时器。

```
click #1 ──┬─ sweep 0/300/800/1500/2600/4200ms
           ├─ hits: m3u8 A, seg-1, seg-2 …
           └─ overlay score 85  → 标记「浮层播放」

click #2 ──┬─ sweep …
           └─ hits: m3u8 B            （与 #1 互不影响）
```

### 4.2 归因规则

- **就近优先**：命中归给「最新且仍在 8 秒窗口内」的会话；新点击一开始，
  旧会话立刻停止扫描（`stale`），避免旧会话把新播放器算到自己头上；
- **会话内去重**：同一会话同一地址只上报一次（`s.urls`）；浮层分数后到时，
  只把该会话已捕获的地址按新分数补报，Dart 侧按会话去重，不重复计捕获次数；
- **会话上限**：单会话最多 24 条命中，防止整页分片刷爆通道；
- **全局上限**：去重表 400 条，超出后重置，避免长页面内存增长；
- **同地址多次点击**：地址只进资源列表一条，`clickHits` 累加，
  列表显示「捕获 2 次」，浮层分数取最高。

### 4.3 资源列表侧的并发

- 被动嗅探先建好的项，被点击命中时**原地补标记**，不新增第二条；
- 分片命中优先挂到「同目录 + 同播放列表」的项上，没有则建分片组；
- 列表上限 60 项，超出裁掉最旧的，避免长列表卡顿；
- 面板提供「浮层捕获 N」筛选，点一下只看这一类。

## 5. 无法直接嗅探时的备选策略

按「能拿到什么」分五级降级，前一级失败自动落到下一级：

| 级别 | 现象 | 处理 | 用户看到 |
|---|---|---|---|
| 1 | 正常 m3u8 / mp4 请求 | 直接归因捕获 | 资源列表新增一项，带「浮层播放」标记 |
| 2 | 请求发生在 Worker / 包装之前 | 扫 `performance` 新增条目做差异归因 | 同上，来源显示 `perf` |
| 3 | 播放器在**同源** iframe 里 | 读 `contentDocument` 递归找 `<video>` | 同上，来源 `iframe` |
| 4 | 播放器在**跨域** iframe 里 | 只上报 iframe 地址 | 面板顶部「跨域播放器 N 个」，点一下在新页面继续嗅探 |
| 5 | MSE / `blob:` 播放 | 发 `mse` 事件 → 自动触发一次手动嗅探 + 补扫 | 提示「直链不可见，已回扫请求记录」 |

再兜不住的情况：

- **手动嗅探**：地址栏菜单 → 手动嗅探当前页，重扫 `performance`、`<video>`、
  `a[href]` 与正文里的 m3u8 链接；
- **重置捕获**：菜单 → 重置点击捕获，会话与去重表清零，重新点一次；
- **明确放弃**：DRM、Canvas 自绘、WebRTC、原生播放器——这些在页面里根本不产生可下载地址。

> 关于「原生层拦截所有请求」：`WebViewClient.shouldInterceptRequest` 能覆盖跨域 iframe
> 与 Worker，但当前 WebView 由 `webview_flutter` 管理，没有暴露该回调；要做需要自建
> PlatformView 或改插件。收益是兜住第 4、5 级的一部分，成本是整条 WebView 链路重做，
> 因此本次不引入，保留为后续可选项。

## 6. 落地实现

### 6.1 文件与职责

| 文件 | 职责 |
|---|---|
| `lib/services/click_sniff_js.dart` | 注入脚本：点击会话、归因、浮层评分、MutationObserver、重置 / 补扫入口 |
| `lib/services/click_sniff.dart` | 消息解析 `ClickSniffEvent`，脏消息一律丢弃 |
| `lib/models/sniffed_media.dart` | 资源项新增 `clickHits` / `overlayScore` / `captureNote`，`kOverlayThreshold` |
| `lib/services/resource_aggregator.dart` | `accept(..., attribution:)`，归因并入已有项，返回 `SniffAcceptResult` |
| `lib/state/app_state.dart` | `onClickSniffMessage`：并入聚合、维护跨域候选、换页清空 |
| `lib/ui/browser_tab.dart` | `ClickChannel`、注入、浮标、菜单说明 / 重置、面板筛选与候选卡片 |
| `lib/state/settings_state.dart` / `settings_tab.dart` | 「点击捕获浮层视频」开关（默认开，持久化） |
| `tool/verify_click_sniff.dart` | 66 项行为断言：解析、聚合归因、脚本约束、接线 |

### 6.2 消息协议（`ClickChannel`）

| `t` | 字段 | 时机 |
|---|---|---|
| `click` | `id, label, tag, x, y` | 每次点击，仅用于序号与提示 |
| `hit` | `id, url, kind, from, delay, score, overlay, label` | 归因窗口内捕获到媒体 |
| `overlay` | `id, score, tag, cls, w, h` | 浮层分数首次越线 / 明显提高 |
| `mse` | `id, from` | 检测到 MediaSource / blob |
| `iframe` | `id, url` | 跨域播放器 |

所有消息附带 `page`、`title`，与既有两路嗅探的字段保持一致。

### 6.3 数据流

```
用户点击
  → pointerdown(capture, passive)
  → begin(): 会话 + 快照 + 6 次扫描定时器
  → fetch/XHR/play 命中 ──┐
  → MutationObserver ─────┼→ hit/overlay 消息 → ClickChannel
  → performance 差异 ─────┘
        ↓
AppState.onClickSniffMessage
  → playlist/segment: aggregator.accept(attribution) → 资源列表（原地补标记）
  → progressive:      只回浮标，不进列表
  → mse:              自动回扫
  → iframe:           面板顶部候选
        ↓
UI：资源列表「浮层捕获」筛选 / 浮标「浮层视频已捕获」/ 菜单说明
```

### 6.4 与其他链路的关系

- 不改 `sniffer_js.dart`、`player_probe_js.dart`、`video_float_js.dart` 的任何逻辑，
  只在最外层多包一次 `fetch` / `XHR.open` / `play`，链式调用照旧；
- 自动接管仍由 `PlayerChannel` 决定；点击捕获只补「列表里的归属与标记」。
  自动接管关闭时，浮层命中会弹一个不打断浏览的浮标作为手动入口；
- mp4 直链不进 HLS 资源列表，避免「统一下载」把 mp4 交给 HLS 下载器。

## 7. 边界与已知限制

- **误判**：广告位也可能在点击后浮层播放。判定只看形态，不看内容；
  缓解办法是面板里按需筛选、按需下载，不做自动批量接管。
- **开销**：`MutationObserver` 常驻 `document.body`，但回调只在活跃会话内工作，
  且每次最多处理 40 个新增节点；无点击时不做 DOM 查询。
- **跨域 iframe**：只能给播放器地址，真正的 m3u8 要等用户在那一页继续嗅探。
- **MSE**：JS 侧只能看到 `blob:`，真实地址依赖 `performance` 是否记录到；
  记录下来即命中，记录不到就真拿不到（这是浏览器沙箱的边界，不是实现缺陷）。
- **加密 / DRM**：`SAMPLE-AES`、Widevine 等仍按原规则拒绝，捕获不会绕过。
